# Лабораторна робота №4 — Міграція бази даних

Виконала: Романюк Юлія, група КМ-41, номер у списку 17.
Варіант: 17 mod 4 = 1 → категорія **«вітер»**.

Технології: Python, SQLAlchemy (ORM), Alembic (міграції), PostgreSQL, MySQL, pandas.
Датасет: [Global Weather Repository](https://www.kaggle.com/datasets/nelgiriyewithana/global-weather-repository).

## Структура проєкту (Layered Architecture)

```
main.py                         запуск програми
presentation/console.py         шар представлення: консольне меню
business_logic/weather_service.py   бізнес-логіка: читання CSV, формула "чи виходити", пошук, копіювання
data_access/database.py         шар даних: підключення до Postgres і MySQL
data_access/models.py           шар даних: ORM-модель (таблиці weather і wind)
data_access/repository.py       шар даних: запити до БД
migrations/versions/            міграції Alembic (0001, 0002, 0003)
datasets/                       CSV-файли
```
Кожен шар звертається тільки до шару під ним: меню → бізнес-логіка → шар даних → БД.

## Як запустити

```bash
pip install -r requirements.txt
docker compose up -d        # запускає Postgres і MySQL (або свої, адреси в data_access/database.py)
```
Покласти `GlobalWeatherRepository.csv` з Kaggle у папку `datasets/`.
(У `datasets/sample_weather.csv` лежить маленький файл з тими самими колонками для перевірки.)

```bash
alembic upgrade head        # створити / оновити структуру БД у Postgres
python main.py              # меню для Postgres
```
```
=== Погодна база (postgres) ===
1 - Завантажити дані з CSV
2 - Показати погоду за країною та датою
3 - Скопіювати всі дані з Postgres у MySQL
0 - Вихід
```
Інші корисні команди Alembic:
```bash
alembic current             # на якій міграції зараз база
alembic history             # список міграцій
alembic downgrade -1        # відкотити останню міграцію
alembic -x db=mysql upgrade head   # те саме для MySQL
python main.py mysql        # меню для MySQL
```

## Гілки (етапи)

| Гілка | Що зроблено |
|---|---|
| `stage-1` | ORM-модель, міграція 0001 — таблиця `weather`, завантаження CSV |
| `stage-2` | міграція 0002 — дані про вітер у таблиці `wind` |
| `stage-3` | міграція 0003 — колонка `should_go_outside` |
| `stage-4` | пошук погоди за країною та датою |
| `stage-5` (`main`) | копіювання Postgres → MySQL |

## Етап 1. Вибрані колонки

| Тип | Колонка |
|---|---|
| текст | `country`, `location_name`, `condition_text` |
| ціле число | `wind_degree` |
| дробне число | `wind_kph`, `wind_mph`, `gust_kph`, `gust_mph`, `temperature_celsius` |
| enumeration | `wind_direction` (N, NNE, NE, … NNW — 16 напрямків) |
| дата | `last_updated` |
| час | `sunrise` |

Категорія «вітер»: `wind_mph`, `wind_kph`, `wind_degree`, `wind_direction`, `gust_mph`, `gust_kph`.

Міграція `0001` створює таблицю `weather` з усіма цими колонками. Якщо запустити `alembic upgrade head`
на порожній базі, Alembic виконає всі міграції по черзі, тобто створить базу з нуля.

## Етап 2. Рефакторинг: окрема таблиця для вітру

Міграція `0002`:
1. створює таблицю `wind` (`weather_id` — первинний ключ і зовнішній ключ на `weather.id`, зв'язок один-до-одного);
2. копіює дані: `INSERT INTO wind (...) SELECT ... FROM weather`;
3. тільки після цього видаляє колонки вітру з `weather`.

Через такий порядок дані не втрачаються. `downgrade` робить усе навпаки: повертає колонки в `weather`,
копіює дані з `wind` і видаляє `wind`.

Особливість: у Postgres enum — це окремий тип `wind_direction_enum`, він уже створений у міграції 0001.
Тому в 0002 стоїть `create_type=False`, щоб Alembic не пробував створити його вдруге.

## Етап 3. Колонка «Чи варто виходити на вулицю»

Формула (за шкалою Бофорта, 10 м/с — це вже «сильний вітер»):
```
не виходити, якщо вітер > 36 км/год (10 м/с) або пориви > 54 км/год (15 м/с)
інакше — можна виходити
```

Міграція `0003` робить три кроки:
1. додає колонку `should_go_outside` (BOOLEAN), яка поки може бути NULL;
2. заповнює її для всіх рядків командою `UPDATE wind SET should_go_outside = CASE ... END`;
3. робить колонку обов'язковою (NOT NULL).

Для нових записів значення рахує функція `should_go_outside()` у `business_logic/weather_service.py` під час завантаження CSV.

## Етап 5. Перехід з Postgres на MySQL

1. На порожній MySQL виконуємо ті самі міграції: `alembic -x db=mysql upgrade head`.
   Усі три міграції пройшли без змін.
2. У меню вибираємо пункт 3 — програма копіює всі рядки з Postgres у MySQL
   (спочатку `weather`, потім `wind`, бо `wind` посилається на `weather`) і показує кількість рядків в обох базах:
```
weather: postgres = 180, mysql = 180
wind: postgres = 180, mysql = 180
```
Після цього маємо дві однакові бази. `alembic current` для обох показує `0003 (head)`.

## Відповіді на питання

**1. Чи можна завантажувати всю базу, а описувати в ORM-моделі тільки деякі колонки?**
Так. ORM працює тільки з тими колонками, які описані в моделі, а інші просто не бачить.
У CSV понад 40 колонок, а ми описали й завантажили тільки ті, що потрібні
(читаємо CSV з параметром `usecols`). Якщо в таблиці БД є колонки, яких немає в моделі,
вони мають дозволяти NULL або мати значення за замовчуванням, бо ORM не заповнює їх при вставці.

**2. Чи є дефолтне значення при створенні колонки «Чи варто виходити на вулицю»?**
Ні. Будь-яке значення за замовчуванням було б неправильним для частини рядків:
TRUE «дозволив» би виходити в шторм, FALSE заборонив би навіть у штиль. Тому колонку спочатку
додаємо з NULL, потім рахуємо справжнє значення для кожного рядка за формулою і лише тоді робимо NOT NULL.
Нові рядки отримують значення від програми під час завантаження.

**3. У скільки етапів ви зробили 3-тє завдання?**
У три кроки в одній міграції `0003`: додати колонку (NULL) → заповнити за формулою → зробити NOT NULL.
Плюс у коді: додали поле в ORM-модель і виклик функції `should_go_outside()` при завантаженні CSV.

**4. На яку частину застосунку ви поклали функцію заповнення колонки?**
На шар бізнес-логіки — функція `should_go_outside()` у `business_logic/weather_service.py`.
Це правило предметної області («чи безпечно на вулиці»), а не робота з БД, тому воно не в моделі
і не в репозиторії. Рядки, які вже були в базі до міграції, один раз заповнила сама міграція 0003
(та сама формула, записана на SQL).

**5. Чи легко було накочувати міграції, перейти з однієї бази на іншу? Які проблеми траплялись?**
Загалом легко: ті самі файли міграцій виконалися на MySQL без змін, треба було лише вказати іншу базу
(`-x db=mysql`). Але довелось врахувати відмінності між Postgres і MySQL:
- **enum**: у Postgres це окремий тип (`CREATE TYPE`), а в MySQL — частина колонки.
  Через це в міграції 0002 довелось додати `create_type=False`, а в `downgrade` міграції 0001 — окремо видаляти тип;
- **дробні числа**: тип `Float` у MySQL зберігає числа з меншою точністю (13.2 стає 13.19999…),
  тому використали `Double`;
- **boolean**: у MySQL немає справжнього BOOLEAN, він зберігається як `TINYINT(1)` (0 і 1);
- **зміна колонки на NOT NULL**: MySQL вимагає повний опис колонки, тому в `alter_column` вказали `existing_type`;
- **регістр**: MySQL порівнює рядки без урахування регістру, а Postgres — з урахуванням,
  тому в пошуку обидві сторони переводимо в нижній регістр (`lower`);
- для підключення до MySQL 8 бібліотеці PyMySQL потрібен пакет `cryptography`.
